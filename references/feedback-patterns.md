# Feedback Patterns

Use this file as the living pattern bank for detailed reviewer feedback. Keep it concise and avoid duplicating the more specific references.

## Durable Patterns

- Treat `体征list` and `需求list` as boss-facing and planning-facing artifacts, not raw analysis dumps.
- Separate symptom evidence from schedulable requirements.
- Use source labels that express importance: `功能Top1`, `体验Top4`, `竞品对比（具体竞品）`, not generic `体征list`.
- Classify with product/business boundaries, not literal wording.
- For supported features that still receive complaints, write support status, likely reason users still complain, and next diagnostic action.
- For optimized issues, compare before/after version percentages and state whether the issue still deserves priority.
- For vague方案, rewrite into `现状/数据 -> 竞品或内部验证 -> 判断 -> 方案`.
- Verify internal app capability when teammates mention existing products such as PDF2 or reader2.
- Use stable competitor identifiers such as brand, developer, or icon-derived names; titles can change.
- Do not add country parameters to links unless the recipient needs that country view.
- Put the main optimization point first, then the specific page or location.
- Sort quantity lists descending when they imply priority.
- Keep count format, punctuation, colors, and blank-cell handling consistent.
